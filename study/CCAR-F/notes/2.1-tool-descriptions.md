# 2.1 Tool descriptions (Domain 2, 18% of the exam)

Code: `study/CCAR-F/day2/tool_descriptions.py`. Groundwork for CCA-P 3.1 (tool and agent configuration).

## What Claude knows about a tool
Only three things: the **name**, the **description** and the **input schema**. It cannot see your code. Every choice between tools is made from that text.

## A good description states
- **Purpose**: what the tool does.
- **Inputs**: what each needs, with an example value.
- **Output**: what comes back, and what does not.
- **When to use it.**
- **When NOT to use it**: the boundary with neighbouring tools.
- **Edge cases**: for example case, unknown names.

## Fixing overlap
Rename tools to specific verb and noun, split a tool that does several jobs, or merge near-duplicates. Watch system-prompt keywords that push Claude toward one tool.

## Exam pattern
When Claude picks the wrong tool, the proportionate first fix is **better descriptions**. Classifiers, routing layers, bigger models and extra infrastructure are the over-engineered wrong answers. If a rule must *always* hold, a description is not enough: use a hook (1.4, 1.5).

## What the experiment showed (Haiku, 10 runs per question)
| Setup | Region question | Price question |
|---|---|---|
| Vague (`weave_lookup` "Looks up weave data", `weave_query` "Queries weave data") | 5/10 correct (a coin toss) | 0/10 correct (always the wrong tool) |
| Clear descriptions | 10/10 | 10/10 |

- First attempt: vague tools with telling names (`search_weaves`, `find_weave_info`) scored 5/5. Claude guessed from the names. Names carry meaning too.
- Two failure shapes: **ambiguity** (a coin toss) and **misleading wording** (consistently wrong).
