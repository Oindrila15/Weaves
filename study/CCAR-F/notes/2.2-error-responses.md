# 2.2 Error responses (Domain 2, 18% of the exam)

Code: `study/CCAR-F/day2/error_responses.py`. Related: F 5.3 (error propagation); groundwork for CCA-P 5.2 (failure modes) and 3.4 (observability).

## Failure is not the same as an empty result
- **Empty result**: the tool worked and found nothing (no weaves in Kerala). A valid answer.
- **Failure**: the tool could not find out (database down). Never return it as an empty list. Claude will treat it as a true fact.

## How to report a failure
- Set the error flag: `is_error: true` on the API `tool_result` (the MCP name is `isError`). It tells Claude "this is a failure, not data".
- Add a **category**:
  | Category | Meaning | Retry? |
  |---|---|---|
  | transient | Temporary: timeout, busy, rate limit | Yes, after a moment |
  | validation | Bad input | Yes, after fixing the input |
  | business | A rule blocks it (no consent, over a limit) | No. Explain or escalate |
  | permission | Not allowed for this user or account | No. Escalate or use other access |
- Add **`isRetryable`** (true or false) and a **message** saying what happened, why, and what to do next.

## Recovery ladder
1. Recover locally first (the tool retries a transient error itself a couple of times).
2. If it still fails, pass it up with structured context: what was tried, what succeeded (partial results), alternatives.
3. Do not stop the whole workflow for one failed part. Note the coverage gap.

## Exam traps
- A generic "Operation failed" or "Error" with no detail.
- Returning an empty list or "success" for a failure.
- Killing the entire workflow on one failure.
- Retrying forever.

## What the experiment showed (one run each, Haiku)
| Case | Tool calls | What Claude did |
|---|---|---|
| 1. Failure hidden as `{"weaves": []}` | 1 | Reported "no data for Tamil Nadu". A wrong diagnosis; the database was down, and nothing told it so |
| 2. Vague `Error` | 2 | Retried once blindly, then gave up and offered general knowledge |
| 3. Transient and retryable | 2 | Retried once and got the answer |
| 4. Permission and not retryable | 1 | Did not retry, explained honestly |
| 5. Validation with a hint | 1 | Claude fixed "TN" to "Tamil Nadu" by itself, so the validation path never fired |

- Cases 1, 2 and 4: Claude filled the gap with general knowledge. Labelled "not verified", but not from our knowledge base. Weaves needs a source and trust level on every fact, so we must decide a policy for this.
- Our consent hook used category `policy`. The exam vocabulary is transient, validation, business, permission, so it should be `business`.

## My weak spots
- Always name the **category** as well as the retry answer. (a) rate limit is transient, (b) no consent is business, (c) misspelt region is validation, (d) account cannot read is permission.
- **business vs permission:** permission is about the *requester* (this account may not read this source). Business is about a *rule on the action or data* (this weaver has not consented, so nobody may see it). Consent is business.
- `isRetryable` means "will the same request work if sent again now?". A condition that might change later (consent given) goes in the message, not in `isRetryable`. Claude cannot make consent change, so for this call it is `false`.
- When asked "what is wrong", state the diagnosis first: the tool hid a failure as a valid empty result, so Claude believes nothing exists. Then give the fix.
- Recovery ladder step 1: the tool retries a transient error itself before reporting it up.
